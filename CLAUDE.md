# wesleybard.com

## Deploy
Pushes to `main` auto-deploy to GitHub Pages via `.github/workflows/deploy.yml`. Build: `npm run build` (outputs to `./out`).
- **Failure emails** come from this workflow. Before 9 Nov 2026 they were real breakages (Google Fonts on 14 and 25 Oct, fixed by moving the fonts into the repo). On 9 Nov a deploy timed out twice in Pages' "syncing_files" step, with the same ~350 MB upload that deployed in minutes all day, so a new push no longer cancels a deploy in progress (cancelling mid-sync can leave Pages stuck; GitHub's template doesn't). **The deploy step can't wait longer than 10 minutes**: the Pages deploy action caps its timeout there, and the 30 minutes set on 9 Nov was cut back to 10 with a warning on every run until 16 Nov, when the setting was put back to 10. So a slow sync still fails and still emails. When a deploy times out, re-run just the failed job (`gh run rerun <id> --failed`): the build is fine, and the site stays on the previous version until it lands.

## Setting up a new machine
A clone carries the playbook (this file), the scripts and the data, but not the tools they run on. Install:
- **Node 25** (`.nvmrc` pins it; `nvm use`). The health importer relies on Node's built-in TypeScript stripping, so an old LTS fails with "Could not load lib/health.ts". Then `npm install`.
- **Python 3 with Pillow** (`pip3 install pillow`) and **Google Chrome** — only for the link-preview card and the weekly share cards, both drawn on request. Importing a week needs neither.
- Push access to the repo (SSH key or HTTPS token). Importing a week is a push.

Smoke-test with `npm test` and `npm run health:add -- --dry-run < /dev/null`.

### Phases, markers and targets
`data/health.json` also holds `phases` (blocks like a cut), `markers` (dated one-off events), `targets` (standing daily numbers), `noteMarks` (glyphs keyed off a day's Notes text) and `calorieTargets` (dated daily calorie goals). These are hand-edited — the import script only touches `days`.

```json
"phases": [
  { "start": "2026-07-20", "type": "cut", "label": "Cut", "goalWeight": 190, "note": "" }
],
"markers": [
  { "date": "2026-08-03", "label": "Deload", "icon": "⚡", "note": "" }
],
"targets": [
  { "from": "2026-07-20", "stepsMinimum": 10000, "stepsGoal": 13500,
    "weighInsPerWeek": 7, "liftsPerWeek": 5, "cardioPerWeek": 3, "note": "Cut begins" }
],
"noteMarks": [
  { "match": "church", "icon": "✝️", "label": "Church" },
  { "match": "orange theory", "icon": "🍊", "label": "Orange Theory", "replaces": "cardio" }
],
"calorieTargets": [
  { "from": "2026-07-20", "cals": 2350, "note": "Cut begins" },
  { "from": "2026-08-10", "cals": 2450, "note": "" }
]
```
- `type` is `cut` | `bulk` | `maintain`. `label` defaults to the type.
- A phase runs until the next one starts; the latest with no `end` is ongoing. Set `end` explicitly **only** to leave a deliberate gap with no phase.
- `goalWeight` is optional. When set, the banner shows distance and percent complete — signed so the same arithmetic serves a cut and a bulk. `goalRemaining` is a magnitude, always positive.
- `ratePerWeek` is optional: the block's planned pace in lb a week, signed (`0.5` on the lean bulk; the cut has none). It draws the plan line on the weight chart and the band on the pace chart, and the change log reports it ("Planned pace").
- To start a new block, append a phase with the new `start`; that automatically closes the previous one. Don't set `end` on the old phase as well.
- **The lead card and the status share card tell the block the newest data falls in** (`leadPhase` in `lib/health.ts`), not just the running one: a block starting on a Monday has no days until the next import, so that week the card closes out the old block ("The cut · Jul 20 – Nov 1 · … Ended at … The lean bulk starts Nov 2.") instead of showing "week 0" and dashes. The weight axis still stretches to the *running* block's goal. The share card numbers weeks within the block, and its ladder climbs for a bulk (start at the bottom, goal on top) and descends for a cut. The cut ran Jul 20 – Oct 25 2026. The lean bulk (goal 220, ~+0.5 lb/wk) started Oct 26 with a refeed week at about 2,700 kcal a day, then 2,900 from Nov 2, then back to 2,700 from Nov 9 on Coach Lee's advice to start the bulk there: Wes moved its start back a week on 9 Nov ("my bulk kinda started the previous week"), and the refeed's 2,700 went in as its own dated target. (The closing-card example above is from the import of 2 Nov, before that move.)
- The "Est. deficit" tile names itself by sign: intake over maintenance reads **Est. surplus**.
- **Every colour reads the block its row belongs to** (Wes alternates cuts and bulks, 9 Nov 2026: "cut then bulk then cut then bulk a lot"). Weekly rows carry `phase` (type, label, start: the block in force on the week's last recorded day, the same rule targets use; `buildWeeklyTrend(days, calorieTargets, phases)`). `weightTone` and `calsTone` in `app/health/components/format.ts` colour by it: a cut wants weight down, a bulk wants weight up, maintenance is neutral; outside every block, down is good, as the tracker began. **Calories against target follow the calendar's rule in every block** (`calorieLight`, since 16 Nov 2026): on a cut, at or under is good, up to 10% over is plain and more is the worse; on a bulk or maintenance, within 5% is good and more than 10% off either way is the worse.   - What shows the block: the log's eyebrow ("Week ending · Lean bulk"), a heading row in Records › By week wherever a block begins (newest first, grouped by the block's start, so two separate cuts stay separate), the lead card, and the status card's per-week colours.

  - **The tiles describe the block the newest data falls in**, never a cut and a bulk blended (16 Nov 2026): Avg calories, Avg protein and Avg steps are the block's averages ("per day, this bulk"), and Tracked is the block's weeks ("3 weeks", "this bulk · 119 days in all"). With no block they fall back to the all-time figures.
  - A **projection** in a later year than the newest weigh-in carries the year ("Oct 4, 2027"): a bulk's goal is usually months out.
- **Weight has its own chart, zoomed to the readings in range** (`WeightTrend`, 16 Nov 2026). From Aug 2026 the axis stretched to every block's goal so the goal lines stayed in view; once the bulk's 220 had to show, the weight line used a third of the height. A goal outside the scale is now a label at the top of its block ("goal 220 ↑ 15.9 lb to go", "goal 195 ↓ ended 5.7 lb short"); one inside the scale is still a dashed `g-goal` line over its own block's days. **Don't stretch the axis to a goal again**: the lead card's track is where the distance to the goal is drawn.
- **The weight line runs through the weekly averages** (one point per Monday–Sunday week, at the week's middle), the numbers every card quotes, with the daily weigh-ins as faint dots behind it. The trailing 7-day line is gone from the chart. The newest, the first and the lowest weekly average in range are labelled.
- **Each block is a labelled band**: alternate blocks tinted, a rule where each one begins, and a label with its name, dates and net change ("LEAN BULK · since Oct 26 · +1.6 lb"), fitted by `FitRow`. The hover tooltip names the day's **Phase**. A block with a `ratePerWeek` also gets a dashed **plan** line from its first weigh-in.
- **Calories sit under the weight on the same dates**: bars above and below a "target" baseline, each day against the target in force that day, coloured by the calendar's rule (on target, close, off target). A bar per day up to 70 days in range (`DAILY_BARS_MAX`), a bar per week beyond that. A ruler over the strip names each target where it took effect ("target 2,450 | 2,700 | 2,900").
- **Pounds per week** (`PaceChart`) is one bar per week, the week's average weight against the week before, on the same day-based x scale and block bands as the weight chart so the two line up. `--accent` is toward the block's goal, orange away from it, grey for maintenance or no change. A block with a `ratePerWeek` gets a band a quarter pound either side of it (`PLAN_BAND`). It shows what the lead card can't: by weekly averages the bulk opened at about +1.1 lb a week against a plan of +0.5, while the lead card's "+0.5 per week" measures from the block's first weigh-in.
- **Goal and calorie target must never look alike** (Wes, 9 Nov 2026: they were both grey dashes and read as one line). A goal weight is long dashes in `--accent`, the weight line's colour, so it reads as weight; a calorie target is grey and dotted (`.g-target`, the next-morning chart's rule at "target").
- `calorieTargets` is the daily calorie target, **dated rather than phase-scoped**: each entry takes effect on its `from` date and runs until the next. The Aug 2026 cut moved 2,350 → 2,450 on Aug 10 without the block changing, which is why attaching it to the phase was wrong. To change the target, append an entry — never edit an old one, or history gets rescored against a number that wasn't in force. Resolver is `lib/calorieTarget.ts` (a module of its own so client components can import it: `lib/health.ts` reads the filesystem), tested in `__tests__/calorieTarget.test.ts`. Steps targets live in `targets` because they are standing habits.
- `noteMarks` draw a glyph in a consistency-grid cell when the day's **Notes** mention the configured phrase (case-insensitive substring). Driven by the sheet's own text so a cross means "church was written down that day", not "it was a Sunday" — an earlier weekday-based version marked every Sunday whether he went or not. `replaces: "cardio"` swaps the orange cardio dot for the icon (Orange Theory instead of the usual treadmill session); without it the glyph draws alongside. They get a legend key but deliberately **no per-date note** — a recurring fact repeated under every chart is noise. Logic is `lib/noteMarks.ts`, tested in `__tests__/noteMarks.test.ts`.
- A marker's `icon` (a single emoji) is drawn in that day's consistency-grid cell (and its day in the log) **in place of the rest dash**. Its note is **taped onto its week in the log** and listed in Records › By week's Notes column (the notes list under the grid was retired with the redesign). Markers are deliberately **not** drawn on the weight chart — that flag was removed on request.

### Goals and streak
Three standing goals live in `targets`, all expressed per week so one rule scores them all: `weighInsPerWeek` (7 = measure every day), `liftsPerWeek`, `cardioPerWeek`. A goal left unset is **not scored**, rather than counted as zero.

**`targets` is a list of dated revisions, not one object.** Each entry has a `from` date and **patches** the one before it, so a revision names only what changed. Append a revision to change a goal — never edit an old entry. This is not decoration: `buildWeeklyGoals` scores every week, so with a single undated object, raising `liftsPerWeek` from 5 to 6 silently re-scored every past week against a rule that was not in force and could wipe out an earned streak. A week that straddles a revision is scored by the one in force on its **last recorded day**, because a weekly count cannot be part-scored. Resolver is `lib/targets.ts` (client-safe), tested in `__tests__/targets.test.ts`.

`buildWeeklyGoals` scores each week; `goalStreak` counts consecutive weeks back from the newest where every goal was met. The newest week is **passed over, not counted against, while it is still filling up** — a Wednesday is not a failed week. The "Goal streak" stat tile and the goals panel at the top of the Consistency section both read from this.

`activeStreak` (consecutive active days, Sunday rest days skipped) is still computed and tested but is no longer surfaced — the tile it used to fill now shows the goal streak. Its rule, if it comes back: Sunday is a scheduled rest day, so an inactive Sunday neither breaks nor extends the run; an unplanned rest on any other weekday does break it; a Sunday that *was* trained counts normally.

Chart rules that are deliberate, not accidental:
- **No dual-axis charts.** The one that existed by permission (weight and calories on two scales, 3 Oct to 16 Nov 2026) was retired when weight got its own chart: calories now sit in a strip under it on the same dates, each on its own scale, so a run of high days and the bump after it still line up. Two measures of different scale get two charts.
- **The range switch** on Trends (8 weeks · This block · Everything, default 8 weeks; `Trends.tsx` owns it, helpers in `trendRange.ts`) redraws Weight, Pounds per week, Steps and Macros. "8 weeks" is the last 56 recorded days; "This block" starts at the first day of the block the newest day falls in, and is left out when there is no block. The cards that always read everything live on Patterns, which has no switch (26 Nov 2026). `Trends` is a client component, so it and everything it imports must be client-safe: `lib/health.ts` reads the filesystem, and derived data comes in as props.
- Weight scale is zoomed to the readings in range, never anchored at zero and never stretched to a goal.
- A weekly point needs at least four of its week's days in range (`MIN_WEEK_DAYS`), so a range that starts mid-week doesn't open on a two-day average.
- Calories are scored against the target **in force that day**, because the target changes mid-block and one flat rule would score early days against a number that wasn't in force yet. The steps chart's floor and goal, and the macros chart's protein goal, are **stepped** lines for the same reason, and the protein count scores each day against its own goal.
- **Steps and macros are weekly averages** (a line with points, `WeeklySeries`) over faint daily dots, on the same day-based x scale and block bands as the weight chart. As a bar per day they had become picket fences. Each line is named at its right end ("Protein 214", "goal 200", "Carbs 329", "Fat 79"), so the legend only keys what isn't named on the chart.
- Rules and targets are neutral inks (`--ink`, `--ink-3`), never a series colour: the bars already carry the series colours. The one exception is a goal weight, drawn in the weight line's `--accent` so it isn't mistaken for the calorie target.
- No entry animation: an animating chart reads as empty on load.
- The range charts label Sundays by short date ("Nov 15"), thinned by `labelStride`.
- On Habits › Daily goals (under the steps chart until 26 Nov 2026), `buildStepStreaks` reports how long the floor and the goal have each been held. Each day is judged against the threshold **in force that day**, so raising a goal cannot retroactively break a run earned under the old one. A day with no steps reading is **skipped, not counted as a miss** — no reading is unknown, not a failure. When the current run *is* the longest, it reads "the best run yet" rather than printing the same number twice.
- The day table draws a heavier rule on the first row of each new week (`.is-week-start`) instead of banding alternate rows.
- Each goal is a meter, not a chart: it is one magnitude against a known ceiling. Met state carries a check glyph and words as well as color.
- `.h-note` uses a 96ch measure with `text-wrap: pretty`. The old 60ch measure wrapped one-line notes short of the card edge and left orphans like "to zero." on their own line.
- **The page opens on one card** (`WeekLead`): the newest week's average weight vs the week before as the headline, the week's other averages beside it, and the running block's story below a rule in the same card: a **track** from the start weight to the goal, filled to the newest week's average with a notch at each week's average, then start · now · change · per week · recent pace · on pace for. It was two cards — weekly averages above a phase banner — but they retold the same story; `PhaseBanner` was folded in and deleted. The headline is never a single weigh-in: Aug 17–23 ended at 204.6 lb after starting at 203.0, which read as a gain even though the week's average *fell* 0.4 lb — one reading moves a pound or two on water, and the page updates weekly, so the week is the unit of progress. The card must read on its own to a visiting coach. The latest reading survives as a stat tile ("Latest weigh-in · one reading"); the "Week over week" and "This week" tiles are gone because the lead says both; "Est. deficit" (maintenance − intake) took the freed slot, keeping the tile grid an even 4×2. Don't restore a single-day headline.
- **Weeks are named for the Sunday they end on** ("Week ending Sep 20"), not the Monday they start. The week is posted after it closes, so that is how Wes refers to it (Sep 2026). The label is built once in `groupIntoWeeks` and every consumer — lead card, goals panel, weekly table, consistency grid, chart axes — reads that one field, so don't relabel a single component back to the start date.
- **The block's "Now" (`currentWeight`) is the newest week's average weight, not the last reading.** Everything hung off it — change, per-week rate, goal remaining and percent, the projection, the status card's ladder — moves with the week, so one watery Sunday cannot undo a week of progress: Sep 27 2026 read 201.5 after a week that averaged 199.5 and the strip said 6.5 lb to go when the week said 4.5. The start stays the first reading (Wes chose this over a first-week average): a block begins on a day. The lead card captions the figure "week avg"; the single Sunday reading still shows in the "Latest weigh-in" tile and the status card footer, each labelled as one reading. A newest week with no weigh-in falls back to the last week that has one.
- The block strip's "Per week" figure is `weightChangePerWeek`: the change divided by the weighed span in weeks, counted inclusively so the denominator matches the "N days tracked" beside it. Null until a full week has been weighed, since a rate from two days is noise.
- **"Recent pace" is `recentChangePerWeek`**: a least-squares slope over the weigh-ins in the trailing 21 days (`RECENT_WINDOW_DAYS`), fitted rather than endpoint-to-endpoint — the first version used the window's two end readings and one watery Sunday swung the projection by months. Null until the phase is older than the window, because until then "recent" and "all-time" are the same measurement. **The projection (`projectedGoalDate`) extrapolates the recent rate once it exists**, falling back to the all-time rate for young phases: five weeks in, the all-time −1.1/wk was front-loaded by the first fortnight's water and promised Nov 22 when the settled ~−0.6/wk pace says early Feb. The whole-block rate deliberately stays endpoint-based — start-to-now is a fact, not an estimate. The status share card shows the recent rate in its "Per week" fact when it exists.
- **`estimatedMaintenance` reads the same trailing 21-day window** (fitted slope × 3,500 under the window's average intake), not the whole span — maintenance drifts as a diet goes on, and the all-span version carried the week-1–2 whoosh forever, overstating the deficit (576 vs the honest ~338 kcal at week 5). The "Est. deficit" / "Est. surplus" tile is maintenance minus the average intake **over that same window** (`recentAvgCals`, "per day, last 3 weeks"). Against all-time intake it blended the cut into the bulk: three weeks into the bulk it read 224 kcal when the surplus was 487.

### The change log
The **Changes** section is `buildChangeLog`, derived from `phases`, `calorieTargets` and `targets` — never hand-written, so it cannot drift from the numbers the charts compute against. That is also why those three carry dates. Consequences worth knowing:
- Every dated entry takes an optional `note`, which becomes the "Why" column. That is the one thing derivation cannot supply — fill it in when changing a target.
- It reads **oldest first**, unlike every other table on the page, because it is a story rather than a snapshot.
- `goalWeight` rides on the phase rather than carrying its own date, so it is reported at the phase start. Changing it mid-phase updates that row rather than adding one; dating it would need the same treatment `calorieTargets` got.
- Markers are deliberately excluded — they are events, not target changes, and the log and Records › By week already list them.


## /snes dataset
Piece 1 of the `/snes` history (spec `docs/superpowers/specs/2026-10-11-snes-dataset-design.md`, plan `docs/superpowers/plans/2026-10-11-snes-dataset.md`). No UI yet; it builds the data pieces 2–5 read.

```
npm run snes                 # everything: fetch → build → box art → build
npm run snes:fetch           # Wikipedia list + chips, review boxes, IGDB, into .snes-cache/ (gitignored)
npm run snes:build           # offline: games.json + companies.json + coverage report (--json for machine-readable)
npm run snes:fetch:boxart    # missing box art → public/snes/box/<slug>.jpg (macOS sips), then build again
```
- **Files:**
  - `data/snes/games.json` holds facts only. Wes's opinions will live in `wes.json`, keyed by the same slug.
  - `data/snes/companies.json`, `aliases.json` and `overrides.json` are the other data files.
  - Parsers are in `lib/snes/`, scripts in `scripts/snes/`.
  - `lib/snes/*.ts` must stay loadable by ts-node from `.mjs`: use `import type` and `.ts` relative imports.
- **Slugs are permanent:** the build reuses the slug already recorded for a game's Wikipedia article (and title, since several games can share one article). Never hand-edit a slug in `games.json`; settle collisions in `aliases.json` `slugs`. **A previous slug that would disappear fails the build** — map the game's new Wikipedia title to it in `slugs`, or, if the game is really gone, list it in `retiredSlugs`.
- **Review scores are SNES-only or nothing.** Boxes put each platform on its own line with a tag (`(SNES)`, `<small>(Genesis)</small>`, `NES:`); `lib/snes/reviews.ts` keeps the SNES segment and drops untagged scores sitting beside another platform's. A redirect to a section of another article (usually a series page) lends no review box. A score lost this way goes back by hand in `overrides.json`.
- **The build also refuses** on Wikipedia rows it can't read (an unfamiliar NA date), stale `aliases.json` entries, and unknown field names in `overrides.json`.
- **Never hand-edit `games.json`.** A correction goes in `overrides.json`, keyed by slug, with a `note` saying why. It is applied last, so a rebuild keeps it. An override or alias naming a missing slug fails the build.
- **The coverage report is the research to-do list:** unmatched IGDB titles, missing box art, possible duplicate companies, and Nintendo Power / EGM coverage. Magazine scores found by hand go in `overrides.json` (`scores.nintendoPower: { score, scale }`, `scores.egm: [..]`).
- **Titles are the US titles as printed.** Wikipedia sometimes lists a game under its European name (*Another World*); the US name (*Out of This World*) goes in `overrides.json` `title`, and its US slug in `aliases.json` `slugs`, keyed by the Wikipedia title.
- **IGDB** needs `IGDB_CLIENT_ID` / `IGDB_CLIENT_SECRET` in `.env.local` (free Twitch dev app). Without them the build still runs with IGDB fields empty. The aggregate score is IGDB `total_rating`, null under 3 ratings.
- **ESRB is null before Sept 1994** whatever IGDB says (re-releases got rated later). `launchTitle` = released 1991-08-23.
- Box art is hosted locally, credited in `public/snes/box/SOURCES.md` (generated from `sources.json`). libretro's arcade-cabinet (`(Arcade)`), `SymbolicLink` and reissue files never count; some files are git symlinks and the fetcher follows them. `__tests__/snes-data.test.ts` fails if two games share a cover file — libretro lacks some sequels, and the near-miss is the first game's box.

The heading names the window ("last N weeks"). The lifts·cardio separator is deliberately wide-spaced so "5 · 3" cannot scan as 5.3. Copy is deliberately dry — facts, no narration; Wes flagged the explanatory captions as reading AI-written.
- `activity` — the week's training: a row per day with a steps bar, the 13.5k goal rule, and chips for lift / cardio / Orange Theory / church.
- `macros` (was `fuel` until Aug 2026) — calories and macros: bar length is the day's logged calories, the segments are that day's macro split. Those two are measured separately (grams x 4/4/9 rarely lands on a logged total), which is why the footer says which is which — don't relabel it as though the segments sum to the bar. A rule in the protein blue marks `proteinGoal` × 4 kcal: protein is the bar's first segment, so a day's blue segment reaching the rule means the grams were eaten. `proteinGoal` lives in `targets` (data/health.json) like the other standing goals, so revising it is an append and it shows in the change log.

Rules that are deliberate:
- **No name, handle or URL on any card.** `/health` is unlinked and `noindex`; printing its address on a public post would advertise it to exactly the audience it is kept from. Don't add attribution back.
- Output goes to `.weekly/` (gitignored). These are posts, not site assets — nothing here is served or deployed.
- Numbers come from `scripts/weekly-stats.mjs`, which reads `lib/health.ts`. Never recompute a figure inside the card script; a card that disagrees with the page is worse than no card.
- Only a **complete** week is drawn. With no finished week the chain exits **3**, which callers treat as a skip, not a failure.
- With `--cards`, card generation runs at the end of `npm run health:add` and can only ever **warn**: the data is already written by then, and a missing Chrome says nothing about whether the week imported.
- The palette is validated against the ink surface, not eyeballed — `#4a95e8` / `#e06a30` / `#2f9e6e` pass the lightness-band, chroma, colour-blind separation and contrast checks. Re-run a validator before changing any of them.
- Type is Outfit only, heavy and tightly tracked. The serif belongs to the site's own cards; these have to read as a scoreboard at thumbnail size.

## /snes time machine
Weekly charts, box office, news and cover art for every week from the SNES launch (1991-08-23) to the last US game, in `data/snes/weeks.json`.

```
npm run snes:pop:fetch   # Wikipedia wikitext (Hot 100, Billboard 200, box office, "YEAR in the United States") → .snes-cache/pop/
npm run snes:pop:art     # album/single/poster page images → public/snes/pop/<artId>.webp (≤240 px) + SOURCES.md
npm run snes:pop:build   # offline: weeks.json + coverage report (--json for machine-readable); exits 1 and writes nothing on errors
npm run snes:pop         # all three
```
  - `.snes-cache/pop/` is the (gitignored) cache; re-runs skip anything already cached unless `--refresh`.
  - `snes:pop:art` fetches covers only for the weeks the Time Machine shows: up to the week of the last US game, plus the two days a week reads chart rows past its start (`assembleWeeks`). It used to fetch all of 1998, which left 16 covers no week used.
  - `data/snes/pop-overrides.json` is `{ "weeks": { "YYYY-MM-DD": … }, "art": { "<artId>": "/snes/pop/x.webp" | null } }`; week keys must be real week starts.
  - Politeness: one request at a time, 2.5 s apart; HTTP 429 backs off 15 s × attempt.
  - `NOW_CPI` (lib/snes) must be updated each January.
- **The Time Machine page** (`/videogames/snes-history/time-machine`, `app/snes/components/TimeMachine.tsx`) and **"Be Kind, Rewind"** on each game page (`BeKindRewind.tsx`) share one newspaper, `Paper.tsx`, whose masthead is **"The Omaha World-Pixel"**. Never use the real Omaha paper's name anywhere.
- **Payload budget:** the Time Machine ships every week and every game to the browser twice (HTML and the RSC payload), so its client props are packed (`lib/snes/pack.ts`) and built in one place (`lib/snes/tmProps.ts`); `__tests__/snes-tm-pack.test.ts` holds them to **≤70 KB gzipped** so the page stays inside the 150 KB page budget. Anything added to the props counts.
- **Fonts:** VT323 and UnifrakturMaguntia (`app/snes/fonts.ts`, `preload: false`) are attached only on the Time Machine, the game pages and the `/videogames` hub (its "On this day" LED) — never site-wide.
- **Credit line:** every SNES page (hub, library, game, company, Time Machine) ends with `SnesCredit` — "Data: IGDB · Wikipedia · libretro-thumbnails", plus the Billboard / Box Office Mojo credit where chart data appears and the CPI-U note where today's money appears. Wes requires it; don't drop it from a page or duplicate it.
- **Price wording:** a price always carries its date and kind — "$199.99 at launch in 1991", "$99.99 in a 1993 catalog" — then "about $X today". Never "then". The Time Machine's console price is the latest complete console package (`CONSOLE_ITEMS` in `lib/snes/prices.ts`) dated on or before the week; accessories never count.
- **Wikipedia links** come from `wikiUrl` in `lib/snes/routes.ts` (titles like "Romeo + Juliet" need encoding); don't build them by hand.
- **Share cards:** `public/og-snes.jpg`, `public/og-videogames.jpg` and `public/og-top8.jpg` come from `scripts/og/build-og.py` (JPEG, 1200×630, ≤300 KB for WhatsApp). The fonts it embeds and their licences are listed in `scripts/og/FONTS.md`.

## /snes top 8
"My SNES Top 8" at `/videogames/snes-history/top-8` (`TOP8` in `lib/snes/routes.ts`): pick 8 games, drag to rank, accept friend requests (recommendations), pick a theme, save a 1080×1080 PNG (`my-snes-top-8.png`). Linked from the `/videogames` hub and the library hero. `noindex`, like every SNES page.
- **Logic:** `lib/snes/top8.ts` is pure (slot state, URL `?g=&skin=&n=`, deterministic recommendations, `slimIndex`). Tests import it through `@/lib/...`.
- **Themes:** `app/snes/top8/themes/*.ts` draw everything in code on a canvas (`render.ts` holds the shared 3×3 layout). **No game logos, no ripped art, and no trademarked game names in theme labels**: the labels are exactly MySpace Classic, Glitter, Console, Grand Prix, Crystal Menu and Polygon Space. Literal colours are allowed inside theme modules; `snes.css` stays tokens-only.
- **Fonts:** Press Start 2P and Orbitron from `app/fonts/` (`app/snes/fonts.ts`, `preload: false`, with fallbacks), attached only on the Top 8 page; VT323 and IBM Plex Sans are reused.
- **Payload:** `__tests__/snes-top8-budget.test.ts` holds the client props to ≤50 KB gzipped (page HTML + RSC ≤120 KB). Anything added to the props counts.
- **Link vs storage:** a shared link (`?g=`) wins on load and is never written to storage; localStorage `snes-top8` is written only after the visitor edits. Every storage access is in try/catch.
- **Share card and hub image:** `python3 scripts/og/build-og.py top8` writes `public/og-top8.jpg` (1200×630, ≤300 KB) and `public/snes/top8-example.jpg` (the hub card's 600×418 example, the 300:209 shape of the other hub cards, ≤80 KB). The script re-draws the MySpace Classic example in HTML (it cannot run the TypeScript renderer), so **if `themes/myspace.ts` changes, update `top8_picture()` in `build-og.py` and re-run it**.
- **One shared Top 8 everywhere:** `app/snes/top8/store.ts` (`useTop8`, `useSyncExternalStore`, server snapshot `null`; same-tab `snes-top8:change` event plus cross-tab `storage`) backs:
  - the ★ (`Top8Star`: a tile or page variant with a full-list replace popover; always a **sibling** of the tile link, never inside the `<a>`)
  - the tray (`Top8Tray`, collapse state in `snes-top8-tray`; not mounted on the Top 8 or Time Machine pages)
  - the library filter `mine=1`
  - the builder's "Browse all games" panel (`Top8Browse`)
  - Lists use `Top8Provider` (one subscription per page). Game and company pages pass a slug→title map. No-art games render `Cover`'s initials placeholder.
- **SNES menu:** `SnesNav` (`current="games"|"time"|"top8"`) sits first in `<main>` on every SNES page (game and company pages count as games), sticky at the top, height `--s-nav-h` (53px). Anything else sticky at the top (the library filter bar, the Top 8 preview) offsets by `var(--s-nav-h)`. The Top 8 n/8 badge comes from the store (client only).
- **Popover focus:** it opens `visibility: hidden` until positioned. Focus only after it's visible (browsers refuse focus on hidden elements; jsdom doesn't notice).
